#+title: Isolated Houdini trial on hypie

This trial starts a second Android container manually. It does not reconfigure
Guix System, replace =redroid-maa=, or reuse that container's game data. The
branch is based on main and does not include the experimental NDK EXEC patch.

* Deploy from lappie

In the repository checkout on lappie:

#+begin_src sh
git fetch origin
git switch --track origin/redroid-houdini-trial
scp scripts/redroid/start-houdini-test hypie.home.labbies.wenxinwang.me:/tmp/uraj-start-houdini-test
ssh -t hypie.home.labbies.wenxinwang.me 'sudo sh /tmp/uraj-start-houdini-test'
#+end_src

The script requires the existing =redroid= Docker network and =redroid-maa=
container configuration. It reuses their host init helper and Intel render
node. It pulls about 961 MB, then starts =redroid-houdini-test= at
=10.203.0.3:5555= with a fresh named volume, =redroid-houdini-test-data=.
No host ports are published. The existing bridge's egress policy still applies.
An occupied address, existing test container, or existing test volume causes
the script to stop instead of silently reusing it.

After startup, ADB on hypie can connect directly:

#+begin_src sh
adb connect 10.203.0.3:5555
adb -s 10.203.0.3:5555 shell getprop sys.boot_completed
#+end_src

Android initially has no game or account data. Install the same official APK,
verify the selected native bridge and actual loaded library, then test cold
starts and login while monitoring screenshots, process exit and CrashSight
records. Do not count an unchanged loading screenshot as success. Only proceed
to MAA account tasks after startup and login work.

* Stop and remove

On hypie, stop the trial without affecting the original container:

#+begin_src sh
sudo docker stop redroid-houdini-test
#+end_src

To resume the same test later, use =sudo docker start redroid-houdini-test=.
It has no automatic restart policy. When finished, these commands remove the
trial container and permanently discard only its game/account data:

#+begin_src sh
sudo docker rm redroid-houdini-test
sudo docker volume rm redroid-houdini-test-data
#+end_src

* First game tests, 2026-10-16

The new instance at =10.203.0.3= initially had no game installed. A crash at
14:40:05 UTC belonged to the old NDK instance at =10.203.0.2=, not this trial.
The same official APK was transferred from the old instance and installed
successfully with =pm install --abi arm64-v8a= in the new one.

The Houdini trial then failed too. At 14:42:50 UTC, after the first-launch
consent screen, Android recorded =tombstone_00=: =sm-thread-http2=,
=SIGSEGV/SEGV_MAPERR= at =0xdead0000=, with six frames in
=system/lib64/libhoudini.so=. The first frame is offset =0x302827=, BuildId
=175be4145090761a44b39a50455fd4976d2d8d3c=. Disassembly shows an intentional
write to the constant address in an internal failure path; the condition
leading to that path has not been identified.

Houdini also logged a linker namespace denial when loading =libart.so=.
A temporary experiment added only =libart.so= to the system default
namespace's link to =com_android_art= in =/linkerconfig/ld.config.txt=,
then restarted zygote. The denial disappeared, but startup still failed:
CrashSight's =tomb_1792161901322.txt= at 14:45:01 UTC records
=FMODAudioDevice=, =SIGILL/SI_USER=, with frames in =boot.oat= and
=system/lib64/arm64/nb/libtcb.so=. This does not establish timebomb expiry
as the cause, nor does it prove the namespace change caused that signal.

The original linker configuration was restored and zygote restarted. No
Houdini binary patch was applied. The game remains installed in the separate
test volume; no login or MAA daily tasks were completed. This image has not
passed startup validation.

* Candidate timebomb branch experiment

On 2026-10-16, the read-only pattern finder from
https://github.com/Vvamp/Libhoudini-hpe-14-timebomb-patch/blob/master/trace.sh
matched one candidate in this exact library: compare at =0x1082dd=, six-byte
=jae= at file offset =0x1082e4= (=0f 83 ef 0d 00 00=), targeting the failure
loop at =0x1090d9=. This heuristic match does not establish that the state
being compared represents expiry in this build.

For a reversible experiment only, those six branch bytes were replaced with
NOPs. The resulting SHA-256 was
=30cac3039f23dc85bd8b48e4addbc0e8d3213708816e66acebe5be8fde1b3181=.
The file was bind-mounted in the test container, zygote restarted, and its
actual mapped file hash checked before the tests.

- Candidate patch alone: startup failed at 14:51:54 UTC; =tombstone_01=
  again reports =0xdead0000= through offsets =0x302827=, =0x1e9e30= and
  =0x108ac3=, this time on the main thread.
- Candidate patch plus the earlier =libart.so= namespace change: startup
  failed at 14:52:50 UTC with =SIGILL/SI_USER=; the ADB screenshot returned
  to the launcher. The patched mapping hash was verified again.

Disassembly of the immediate failure path shows that =0x1e9c98= calls
=0x30e170=, which looks up address/page bits (shifts by 32, 17 and 12,
then a bit test). A zero result branches to the intentional crash helper.
This is a more specific lead than the sentinel address alone; it does not
exclude an earlier expiry-related state change.

Both experiments failed, so neither change is included in the startup
script. The bind mount was removed, original linker configuration restored,
and zygote restarted. Both original hashes were verified after restoration.
