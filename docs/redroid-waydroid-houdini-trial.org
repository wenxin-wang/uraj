#+title: Waydroid Houdini on the Codysk Android 13 base

* Why this trial

The unmodified Codysk NDK image failed on the third launch of Arknights
2.7.81. The earlier ERSTT Houdini trial used ChromeOS Houdini 11.0.1f_z.
User-provided community reports specifically recommend the Houdini payload
from =casualsnek/waydroid_script= instead of =redroid-script=.

On 2026-10-16, the Android 13 entry in
https://github.com/casualsnek/waydroid_script/blob/main/stuff/houdini.py
points to =supremegamers/vendor_intel_proprietary_houdini= commit
=2f8f088671182e17e67321e098e8411a3972a628=.
That commit imports HPE =UKW1.260829.001=, with Houdini
=14.0.0_y.GoogleGame_com1.3= and Houdini64
=14.0.0_z.GoogleGame_com1.3=. This is not the earlier ChromeOS build.
The community reports do not identify their exact commits, so this trial
uses the current pinned upstream payload, not a claimed exact reproduction.

* Implementation

The startup script downloads a fixed, SHA-256-checked archive and builds a
local image on the pinned Codysk Android 13 base. It removes the NDK guest
library trees, translator/proxy libraries, program runners and init script,
then copies the complete Houdini prebuilts into /system. This avoids mixing
NDK guest libraries with Houdini's replacements. The Houdini init script's
binfmt configuration paths are adjusted from /vendor to /system, matching
the installation location used by waydroid_script. No binary patches or
linker namespace changes are applied.

Runtime properties select =libhoudini.so=, both ARM ABIs and their x86 ISA
mappings. Existing Intel render-node and host-protection init mounts are
retained. The base is fetched through =ghcr.nju.edu.cn= with the same pinned
manifest digest as the original Codysk trial.

* Deploy from lappie

On the existing =redroid-houdini-trial= branch:

#+begin_src sh
git pull --ff-only origin redroid-houdini-trial
scp scripts/redroid/start-waydroid-houdini-test hypie.home.labbies.wenxinwang.me:/tmp/uraj-start-waydroid-houdini-test
ssh -t hypie.home.labbies.wenxinwang.me 'sudo sh /tmp/uraj-start-waydroid-houdini-test'
#+end_src

The host needs Docker, curl, tar, sed and sha256sum. The new container is
=redroid-waydroid-houdini-test=, ADB =10.203.0.5:5555=, with a fresh volume
=redroid-waydroid-houdini-test-data=. Existing names, volumes or IP allocations
cause refusal rather than data reuse. The original game container is not
changed. This is a manual trial; it does not require system reconfiguration.

* Validation

Archive inspection and shell syntax checks precede deployment. Docker build,
boot and game compatibility still require runtime verification on hypie.
After boot, verify both the selected property and mapped library hash before
installing the same ARM64 APK. When copying Bundles, set ownership to the
new package UID rather than retaining the old container's UID. Monitor
screenshots, process liveness, logcat and CrashSight records together.
Login and battle tests follow startup; no MAA account tasks have run here.

Stop the test with =sudo docker stop redroid-waydroid-houdini-test=.

* Build-shell correction

The first host build failed before producing an image: executing
=/system/bin/sh= returned ENOENT. Android's ELF interpreter lives in APEX,
which is not mounted during Docker build. The build now copies a static
BusyBox from a digest-pinned official =busybox:1.37.0-musl= stage and uses
its shell and rm directly. It removes the temporary tools after cleanup.
This adds a Docker Hub pull of about 871 KB for the amd64 tool layer.

The downloaded amd64 BusyBox was checked for absence of PT_INTERP and run
inside an otherwise empty chroot in the test container. Shell execution,
file cleanup and self-removal succeeded without Android libraries or APEX.
Full Docker build remains to be rerun on the host.

* Initial runtime checks, 2026-10-16

The host build with static BusyBox succeeded and the new container booted.
ADB confirmed =libhoudini.so= was selected and mapped by zygote64, with the
expected =5ef64035...= hash. SurfaceFlinger used Intel HD 630 / Mesa 24.0.8.
The same ARM64 version 2.7.81 APK was installed.

The first game launch failed at 16:49:21 UTC before the consent screen:
Houdini initialized but the system default linker namespace denied access
to =/system/lib64/arm64/libtcb.so=. Houdini logged error =0x0190015a= and
aborted. This was an integration issue before game startup.

For the runtime experiment, the original =/linkerconfig/ld.config.txt= was
saved and the following line appended at the end of its =[system]= section
(after all existing default permitted-path assignments):

#+begin_example
namespace.default.permitted.paths += /system/${LIB}/arm64:/system/${LIB}/arm
#+end_example

After restarting zygote and waiting for activity services, the game reached
the consent screen and then resource selection. No game crash record or
orphan game process was observed in that launch. This change is temporary:
container boot regenerates linkerconfig. The image startup script does not
yet include this integration fix. No binary patches were applied.

With the namespace correction, five manual cold launches reached either
resource selection or active resource updating. No new game native crash
was observed, and the final process snapshot had no orphan game processes.
These are startup observations with differing resource states, not a
controlled stability benchmark. Login and battle remain untested.

Bundles and HGGameUpdate were copied from the original instance, then their
ownership corrected to the new app UID (10077). The game still requested
resource updating. Two reversible experiments did not eliminate that update:
copying only the V078 resource-grading preference, and regenerating the
HGGameUpdate cache. Both experiments were rolled back. At 17:05 UTC the
last launch remained alive, updating at 2660 / 14942 MB (18%). The game was
left running to continue the update. No account data was copied and no MAA
account tasks ran. The namespace correction remains only in the running
container and must be reapplied after container restart.
