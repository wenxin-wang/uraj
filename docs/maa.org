#+title: Arknights automation

* Deployment with redroid

** Design

hypie's installed system runs =redroid-maa= under Docker (not the live
installer).  Guix declares the container and its dependencies; Shepherd manages its lifecycle.
Android's =/data= is bind-mounted from
=/var/lib/redroid/data/maa-houdini-13= on the system disk.  Other Android instances must have separate names, data
directories and IP addresses.  Guix generation rollback does not roll back
Android data: stop the instance and back up its data before image upgrades.

Use the Intel HD 630 for rendering, not the GTX 1080.  Resolve the Intel
render device by PCI identity rather than assuming =renderD128=.  The host
kernel must support Binder; use memfd instead of the removed ashmem driver.

** Networking

Production addressing (checked against current IPv4 routing tables on start):

| Object      | Value           |
|-------------+-----------------|
| Docker net  | redroid         |
| Host bridge | br-redroid      |
| Subnet      | 10.203.0.0/24    |
| Gateway     | 10.203.0.1      |
| redroid-maa | 10.203.0.2:5555 |

These are defaults in =(uraj services redroid)=.  If a LAN or VPN overlaps,
change the network's subnet/gateway and the instance address together.

Use a dedicated Docker bridge with an independent network namespace for
Android.  Do not use host networking: Android manages routes and networking
inside its namespace, and its ADB daemon must not listen on the host's LAN
interfaces.  Do not publish container ports.

Guix's shared [[file:restricted-network.org][restricted-network service]] owns IPv4 forwarding and
nftables tables for egress masquerading and filtering.  Docker's automatic
iptables/ip6tables, IP forwarding and userland proxy management are disabled.
The default Docker bridge is disabled; the redroid network is explicitly
provisioned.  Rules must not flush or replace unrelated host/VPN rules.
Unsolicited forwarding into redroid is blocked; the host can connect
directly to the instance's private IP.  The private subnet must not overlap
the host's LAN or VPN routes.  Wi-Fi and Ethernet use the same routed design.

hypie's fwd2home is a full tunnel (strongSwan's =from all lookup 220=), which
captured the bridge subnet in both directions: ADB from the host timed out
and Android's DNS failed.  hypie therefore sets =vpn-bypass-priority= to
200, so the restricted-network service adds =to 10.203.0.0/24 lookup main=
ahead of it; startup checks that the subnet routes through =br-redroid=.  Reconfiguration does not restart the
running service; apply such changes with =sudo herd restart
restricted-network=, then start the dependent redroid instance again.

Only =inet restricted_network= and =ip restricted_network= are replaced,
atomically.  Stopping the network services retains protection; it never
deletes other instances' network.  Unrelated firewall tables are retained.
An existing host firewall can still reject forwarding: its policy must also
permit the intended traffic.  Containers may initiate public TCP/UDP
connections, but cannot access LAN/VPN/private destinations or host services.
DNS on TCP/UDP 53 is restricted to the configured resolver.  Host-started
ADB connections and their replies are allowed.  Containers on the same bridge
are not isolated from one another at layer 2; only trusted Android instances
should share it.

The =network= field of =redroid-configuration= holds a =restricted-network=
record, defaulting to =%redroid-network=.  The redroid service contributes
this record directly to =restricted-network-service-type=; no separate
redroid network service or field-conversion layer is needed.

#+begin_src scheme
(service restricted-network-service-type)
(service redroid-service-type
  (redroid-configuration
    (network
     (restricted-network
       (inherit %redroid-network)
       (egress-interfaces #t)))
    (auto-start? #f)))
#+end_src

Set the embedded network's =egress-interfaces= to =#t= or the actual uplink
list; the empty default permits no new outbound traffic.  Public LAN/VPN
prefixes and public addresses that hairpin to private services must be added
to the policy's =blocked-destinations=.  The container network name comes
from the same record.  Docker's =--dns= options and Android's numbered DNS
boot arguments both use its policy's =dns-servers= list, which defaults to
='("114.114.114.114")=.  Redroid requires an explicit nonempty IPv4 list: =host=
snapshots are unavailable when its Android boot arguments are generated.
Egress follows the host's forwarding/routing policy; host-only proxy settings
are not automatically used by Android.  Split-tunnel VPN behavior needs
device testing.

** Control plane

=maa-cli=, MaaCore and adb run outside Android under a separate scheduled
job at 02:00, 05:00, 11:00, 14:00 and 21:00 Asia/Shanghai. They connect to the
private Android IP on port 5555. The game must already be manually logged in.
Changing the controller to mower later does not require replacing Android
or its persistent data.

** Scheduled daily tasks

The installed hypie system includes =%maa-services= from
=src/guix/uraj/services/maa.scm=; the live installer does not. Reconfigure
hypie to activate it. mcron uses hypie's inherited =Asia/Shanghai= timezone
and runs at minute zero of each configured hour; missed runs are not replayed.

=env/maa/tasks/daily.toml= restores the previous daily configuration:
Official client login, 3/4-star recruitment (leave 5/6-star tags for manual
handling), preset base rotation and clues, friend visits and credit shopping,
rewards, then close the game. There is no =Fight= task and =credit_fight= is
false, so this round does not spend sanity. Base rotation uses the game's
existing preset queues; keep those configured in-game. Drones accelerate
Pure Gold production (=drones = "PureGold"=).

The dedicated =maa= system account keeps state under =/var/lib/maa=, with
ADB server port 5038 separate from interactive clients. A nonblocking lock
prevents overlapping runs, and a two-hour timeout bounds a stuck run.
Start the ADB server explicitly before MaaCore: in the first live test,
letting MaaCore spawn it left a communication pipe open in the background
server and delayed connection by a minute. Prestarting it connected in one
second. Both startup and MAA run inside the lock and timeout.
The command's =PATH= includes both ADB and =bash-minimal=: MaaCore's
PosixIO invokes =sh -c= through =execlp=. An ADB-only =PATH= lets the
absolute-path server startup succeed but makes subsequent device commands
fail with =exec failed: No such file or directory=.
Configuration and the pinned MAA 6.19.0 package are immutable store files;
resource updates and logs go to the account's writable data/cache/state
directories. CLI logs are under =/var/lib/maa/state/maa/debug/=; scheduler
output is in =/var/log/mcron.log=. Inspect upcoming runs with
=sudo herd schedule mcron 8=.

maa-cli 0.7.5 also performs a mandatory API hot update before task parsing,
including during =--dry-run=; this needs outbound HTTPS. The optional
MaaResource Git update warns on failure, but an API update failure aborts
that run. See the [[https://github.com/MaaAssistantArknights/maa-cli/blob/v0.7.5/crates/maa-cli/src/run/mod.rs][pinned CLI run implementation]].

The scheduled command sets =SSL_CERT_DIR= to the =nss-certs= store
directory and clears =SSL_CERT_FILE=. This package contains individual
certificates, not =etc/ssl/certs/ca-certificates.crt=. The 2026-10-17
21:00 scheduled run pointed at that nonexistent bundle and aborted with
=No CA certificates were loaded from the system=. Interactive validation
does not validate the scheduler's certificate environment; after deploying
the fix, check the dedicated account's scheduled invocation as well.

Live validation on hypie on 2026-10-17, 16:20--16:25 Asia/Shanghai, used
the Guix store MAA/ADB binaries and this task/profile/CLI configuration

=redroid-maa-image= one-shot service builds a local image from the official
Android 13 amd64 base, pinned to
=sha256:524987f1fc489f6018e2c9d0dd622e5eccea13eb896417cb4bfb26bc3fea9afd=
(=redroid/redroid:13.0.0-latest=, checked 2026-10-17).

** ARM translation

hypie selects =redroid-houdini= and =native-bridge-library "libhoudini.so"=.
The package pins the Android 13 payload selected by waydroid_script at
[[https://github.com/supremegamers/vendor_intel_proprietary_houdini/commit/2f8f088671182e17e67321e098e8411a3972a628][commit 2f8f088]],
HPE UKW1.260829.001 / Houdini 14.0.0 GoogleGame com1.3. The archive is
SHA-256 checked, and the binaries are neither patched nor stripped.
The expected 64-bit library hash is
=5ef64035ec89bca3d5e33b9f3b6556f98f6c11d11957387d403ae4a4d7cc40ec=.

The package installs the native bridge and its ARM guest libraries. It omits
ARM executable runners and binfmt_misc registration, which would affect the
host and is not required for app native-library translation. Explicit boot
properties select Houdini, ARM ABIs and their x86 mappings. The old NDK
libraries, guest trees, linker configurations and init script are removed
before copying Houdini into the image. A Guix-built static BusyBox performs
this build step: Android's own shell cannot run before APEX is mounted.
The temporary BusyBox and preparation script are then removed.

Houdini requires the default system linker namespace to permit
=/system/${LIB}/arm64= and =/system/${LIB}/arm=. An init service adds these
paths at the end of the generated =[system]= section, idempotently. The
image build inserts it before both explicit =start zygote= and
=class_start main=; official redroid leaves =ro.crypto.state= unset and uses
the latter path. Init waits for =uraj.houdini.linker.ready= to become =1=.
A missing/duplicate system section or failed helper leaves zygote blocked
for diagnosis instead of silently booting without the correction.

** Move from the trials to production

The tested, logged-in instance at =.5= uses
=redroid-waydroid-houdini-test-data=. Before reconfiguring, copy that stopped
instance's complete data, including resources and account state, into the
new production directory. Never open the Android 11 directory with Android
13. On hypie:

#+begin_src sh
sudo sh scripts/redroid/migrate-houdini-data
sudo herd stop redroid-maa
# Reconfigure/deploy hypie from this revision using the usual deployment tool.
sudo herd start redroid-maa
sudo docker exec redroid-maa getprop sys.boot_completed
sudo docker exec redroid-maa getprop uraj.houdini.linker.ready
#+end_src

The migration refuses an existing destination and retains the source volume
on any copy failure. The old Android 11 directory stays intact for rollback.
After confirming login on =10.203.0.2:5555= and restarting the production
service once to check the persistent namespace hook, retire the trials:

#+begin_src sh
sudo sh scripts/redroid/retire-trials
#+end_src

This checks the migration marker, production data mount, boot completion,
Houdini selection and namespace readiness before stopping/removing the four
named trial containers and their named volumes (=.3= through =.6=). It never
uses =docker prune=, and keeps production and the old Android 11 data.
The local trial image tags are removed when no container references them;
shared base image caches remain. These host actions require Docker/root
access; they are not performed by reconfiguration itself.

** Runtime evidence and remaining checks

The same HPE library on the Codysk Android 13 base passed account login,
a short TR-1 battle-loading test and MAA daily tasks on 2026-10-17. The
unmodified Codysk NDK image and earlier ChromeOS Houdini 11 failed startup.
The official Android 13 base with this HPE payload completed three initial
launch observations without native crashes; the first and third reached
resource selection. The daily validation above subsequently confirmed login
and MAA on production; battle was not repeated on that base. The
first official trial exposed the missed =class_start main= hook; the helper
was then applied manually and successfully invoked through init. The fixed
boot hook still needs a full production restart check. The production
package additionally omits host-global binfmt registration; it does not
change the library binaries. These limits remain explicit even though this
configuration now replaces the trial setup.

Before reconfiguration, on hypie:

#+begin_src sh
grep binder /proc/filesystems
ls -l /dev/dri/by-path/pci-0000:00:02.0-render
ip -4 route show table all
#+end_src

The pinned Guix x86_64 kernel configurations include Binder and binderfs.
The running kernel still needs checking.  If binderfs is missing, load
=binder_linux= if it is a module, or rebuild/boot a kernel with Binder enabled.
No extra Binder DKMS module or ashmem driver is installed by this service.

The Intel device is bind-mounted at =/dev/dri/intel-render= inside Android.
The container is privileged, as in the upstream deployment recipe.  A
small statically linked entrypoint first bind-mounts =/proc/sys/kernel/modprobe=
read-only inside the container, then executes =/init androidboot.hardware=redroid ...=.
If that protection fails, Android is not started.  This avoids both Android
disabling host module autoloading (upstream [[https://github.com/remote-android/redroid-doc/issues/932][issue #932]]) and runc's rejection
of OCI mounts at that =/proc= path.  Its behavior still needs runtime validation
against the selected Android image.
The helper is built from =src/guix/uraj/packages/aux-files/redroid-init.c=.
It avoids depending on Android's shell/APEX libraries before init has run.

** Mower packaging investigation, 2026-10-18

Inspected release =v4.1.6-alpha.12=, resolved to commit
=0e151ae323923952683a173b8f073c8ff8103a92=. This is a packaging investigation,
not a deployed or runtime-validated Mower package.

The Linux x64 release is a 237,832,981-byte tarball. Its
[[https://github.com/ArkMowers/arknights-mower/blob/0e151ae323923952683a173b8f073c8ff8103a92/webui_zip_for_linux.spec][PyInstaller specification]] uses EXE with =exclude_binaries=True= and
COLLECT: dependencies live beside the executable in =_internal/=, rather
than inside a one-file executable that unpacks them at startup. This makes
patching the host ELF files during a Guix build plausible. The existing
=maa-assistant-arknights= package provides a useful pattern, but Mower needs
its own dependency audit, including libraries loaded dynamically and
preservation of private library search paths. Android payloads must not be
patched as host executables.

The main obstacle is the desktop entrypoint, not ELF rewriting. In
[[https://github.com/ArkMowers/arknights-mower/blob/0e151ae323923952683a173b8f073c8ff8103a92/webview_ui.py][webview_ui.py]], =_run_desktop= unconditionally calls
=exit_if_webview_backend_missing=. Setting =MOWER_BACKGROUND=1= suppresses
the window but still enables the tray. =MOWER_MANAGED=1= only suppresses
the tray while a manager remains registered. These switches therefore do
not provide a clean standalone headless service. The release workflow
tests a GUI launch under Xvfb; that does not establish headless operation.

=MOWER_DATA_DIR= is supported by =utils/path.py=, so configuration and
state can be kept outside the immutable store. Software/resource update
paths and MAA subprocess startup still require validation before a native
package could be considered ready.

The upstream
[[https://github.com/ArkMowers/arknights-mower/blob/0e151ae323923952683a173b8f073c8ff8103a92/docker/Dockerfile][docker/Dockerfile]] is a more direct headless route: Python 3.12, a built
WebUI, server dependencies, and Flask's =server:app= entrypoint. It differs
from the repository-root Dockerfile, which builds a desktop executable.
Its entrypoint downloads the latest MAA when =/MAA= is empty; a pinned
deployment must supply MAA explicitly. Base images and the uv image also
need pinning; fixing the Mower commit alone does not fix those inputs.

Selected approach: use the server container for the initial deployment.
A native Guix package remains possible, but should first demonstrate a
clean headless entrypoint, HTTP startup, writable-state separation, and
MAA worker startup. Merely getting the patched executable to launch would
not cover these requirements. Source files were inspected; the slow binary
download was stopped before completion, so no full archive checksum,
complete ELF audit, or runtime test was performed.

** Mower container commissioning

=env/mower/= supplies a headless Docker recipe and startup wrapper;
=(uraj packages mower)= generates its context from the hash-verified source
archive above and the original MAA 6.19.0 archive. No upstream source patch
is applied. Python and Node base images are pinned by digest. Python uses
upstream's pinned server requirements and the UI uses =npm ci=. Apt package
repositories and Python build dependencies are still network inputs, so
this is not a fully reproducible/offline Docker build.

Build the image on hypie (or another x86_64 Docker host):

#+begin_src sh
builder=$(guix build -L src/guix -L src/guile \
  -e '(@ (uraj packages mower) %mower-build-image)')
sudo "$builder"
#+end_src

The builder records the Guix context path in the image's =uraj.context=
label and rebuilds when it changes. Image building uses host networking
because hypie disables Docker's default bridge. The running container
uses the private =redroid= network at =10.203.0.3=, with an explicit ADB
grant to =10.203.0.2:5555=. It has no published ports, privileged mode,
GPU access, or Docker socket.

After deploying the updated hypie system configuration:

#+begin_src sh
sudo herd start mower
# From the workstation:
ssh -N -L 58000:10.203.0.3:58000 wenxin@hypie.home.labbies.wenxinwang.me
#+end_src

Open =http://127.0.0.1:58000=. The generated WebUI token is in
=/var/lib/mower/config/conf.yml= under =webview.token=; read it privately
over SSH. It is not included in the store, image, or startup log. Mower
configuration, roster, Skland credentials, reports and application logs
live under =/var/lib/mower= (mode 0700). The MAA resource cache is preserved
in its =maa-cache/= subdirectory. MAA core updates belong in the image
recipe; do not use the WebUI's software/core updater for this deployment.

The service starts the HTTP UI only. It does not start the game worker.
Initial settings select official-server redroid, ADB screenshots and
MaaTouch, and leave the stage plan disabled. Configure the roster and
Skland account in the UI, then set the threshold, interval and current
activity stage before enabling the plan. No automatic 1-7 farming is
enabled during commissioning. The agreed strategy is threshold-based
farming, activity-stage navigation with 1-7 fallback, and a weekly
annihilation run; there is no longer a separate 02:00 drain requirement.
Navigation fallback and annihilation behavior still need device testing.

While the container is running, its entrypoint holds the same host inode
as maa-cli's =/var/lib/maa/daily.lock=. Thus mcron jobs skip even when the
Mower game worker is paused. If an old MAA job is already running, Mower
exits with code 75 before initializing its worker; wait for that job to
finish before starting Mower. Stop the container with =sudo herd stop mower=
to release the lock and allow the old scheduled jobs to run again. Do not
replace or delete the lock file while either controller is running.
This lock does not cover arbitrary manual ADB clients.

Mower and its preparation/image services default to =auto-start? #f= in
hypie's configuration. Enable automatic container startup only after
commissioning. Upstream's Flask entry still needs an explicit WebUI/API
start of the game worker after a container restart; automatic worker
resumption and pause persistence are separate follow-up work.

Slack is also follow-up work: SMTP reception plus logs, commands for
stage/pause/resume/screenshot, one thread per game day (04:00 Beijing),
detailed decisions and execution results, daily reports at 22:00 and
Sunday weekly reports at 22:00. No Slack credentials are needed for this
container phase.
