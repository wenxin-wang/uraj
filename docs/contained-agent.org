#+title: contained-agent: coding agents in per-project Guix containers

=contained-agent= runs a coding agent (Codex, Claude Code, OpenCode, Pi) inside
=guix shell --container=.  The container shares only the current project
and the parts of the agent's own state that must persist.  The same command
serves interactive use in a terminal and Paseo, which launches agents
remotely.

The threat model is an agent that follows instructions it reads in logs,
web pages or third-party code (prompt injection), or that makes a well-meant
destructive change.  The sandbox has to hold without the agent's
cooperation.

* Components

| Path                                                      | Role                                                         |
|-----------------------------------------------------------+--------------------------------------------------------------|
| =src/guile/uraj/bin/contained-agent.scm=                  | The program: plain Guile, no =(guix ...)= modules            |
| =src/guile/uraj/bin/contained-ssh.scm=                    | Host-side per-project ssh-agent lifecycle and key loading   |
| =src/guix/uraj/home/llm.scm=                              | Agent specs, package list, =program-file=, Home files        |
| =env/dotfiles/llm/contained-agent/.config/contained-agent/projects.scm= | Per-project clauses, owned by the user                      |
| =~/.local/state/contained-agent/=                          | Approved copies of project-local files                       |
| =~/.config/contained-agent/projects.local.scm=              | Optional host-private central additions, never Home-managed  |
| =/run/secrets/contained-agent/projects.scm=                 | Optional host-private central additions, decrypted by SOPS   |

The program calls the =guix= command (=guix shell -C ...=) rather than Guix
modules.  =llm.scm= generates the entry point with =program-file= and passes
in everything known only at build time: store paths of the real =codex=,
=claude=, =opencode= and =pi=, of =git=, the agent specs and the package
list.  Home installs:

- =~/.local/bin/contained-agent=
- =~/.local/bin/codex=, =~/.local/bin/claude=, =~/.local/bin/opencode=
  and =~/.local/bin/pi=: store items that are
  themselves links to =contained-agent=, made with =computed-file=.

The program dispatches on the name it was invoked as (minus a store hash
prefix).  Under an agent's name it takes exactly that agent's arguments;
as =contained-agent= the first argument names the agent, or is =allow= or
=inherit=.

* Use

- Terminal: =~/.local/bin= comes first in =PATH= (=.profile.d/61-paths.sh=),
  so =codex=, =claude=, =opencode= and =pi= are the contained ones.
  The originals remain at =~/.guix-home/profile/bin/=.
- Paseo: Home activation configures daily broker clients in =~/.paseo/config.json=
  (see [[file:paseo-daemon.org][daemon service]]):
  #+begin_src json
  "agents": { "providers": {
    "codex":  { "command": ["/home/wenxin/.guix-home/profile/bin/paseo-codex-daily"] },
    "claude": { "command": ["/home/wenxin/.guix-home/profile/bin/paseo-claude-daily"] },
    "pi":     { "command": ["/home/wenxin/.guix-home/profile/bin/paseo-pi-daily"] } } }
  #+end_src
  Paseo's OpenCode runs on the host only (=opencode-host=): one shared
  server handles all workspaces, which no project container can hold.
  Restart the daemon after a change: it caches the provider version probe.
- Approve a project's own files: =contained-agent allow [DIRECTORY]=.
- Approve a new worktree as its source checkout (see [[Inherited approvals]]):
  =contained-agent inherit [DIRECTORY]=.

* The container

- =--container --no-cwd --network --expose=/gnu/store=.  The whole store is
  read-only, so store links in configuration (MCP servers, skills) resolve.
- =/usr/bin/env= links to the profile's =env= (=--symlink=), as on Guix
  System, so =#!/usr/bin/env= scripts run.
- The environment is cleared; agent specs and projects list what to keep
  (=--preserve=).  =SSL_CERT_FILE= and friends point at the profile's
  =nss-certs=.
- Packages: =%agent-tool-packages= in =llm.scm= is shared with Home and
  currently includes =agent-browser=.  The launcher imports a manifest of
  these exact package builds, so the CLI matches the Home-installed skill
  without depending on the runtime Guix channels.  Add shared agent tools
  to this list.  =%contained-agent-packages= adds the container's base tools,
  alongside an approved project manifest.  The defaults include Python,
  Perl, =bc=, =curl=, =wget=, =jq=, =file= and common archive tools, alongside
  Git, =fd= (so Pi need not download it each session) and shell utilities.
  =bubblewrap= provides =bwrap=, needed by Codex's
  own command sandbox and by the overlays below.  Changes to the default package list
  take effect after Home reconfigure and starting a new agent session.
- The network is still the host's (=--network=).  An allowlisting proxy is
  future work; see [[*Open items]].
- All agents can read =~/src= when it exists, including other repositories
  and their uncommitted files.  Common mounts come first; the current work
  tree is then mounted read-write, followed by its Git protections.  Other
  projects remain read-only unless separately granted write access.
- All agents can read =~/.cache/paseo-tmp= when it exists. Paseo uses it as
  =TMPDIR= so Codex's =localImage= paths work across container boundaries.
  This includes other sessions' attachments and temporary files; see
  [[file:paseo-daemon.org::*Image attachments][image attachments]] for setup and cleanup.
- All agents can also read =~/.paseo/uploads=, where Paseo stores file
  attachments such as PDFs. Only this subtree is exposed read-only; the
  remaining Paseo state stays private. This includes uploads from other
  sessions. Activation and daemon startup create the directory before agents
  launch; new uploads remain visible through the directory mount.
- Clone temporary reference code into =/tmp/reference-code/=, or use an
  ignored =.reference-code/= directory in the current work tree to retain it.
  Read access to =~/src= does not grant permission to clone into it.

** Working directory

Paseo starts =codex app-server= from its own working directory, =$HOME=,
and tells Codex the session directory over JSON-RPC.  Claude and Pi are
started with
the session directory as working directory.  All get =PASEO_AGENT_CWD=.
Every process below an agent inherits that variable, so it is trusted only
when the working directory is =$HOME=.

A working directory of =$HOME= or =/= shares no project at all: Paseo's
helper app-servers (model lists...) run that way.

Projects are mounted at their host path.  A fixed path such as =/work/proj=
does not work: Paseo passes host paths to the agent.

** Git

The work tree and the repository's common git directory are separate
read-write mount points.  Read-only mount points on top cover what makes
host-side git run code or read other files:

- =hooks/= and =config= of the common directory;
- a linked worktree's =.git= file;
- =worktrees/= as a whole, then the session's own worktree directory
  read-write again, with its =commondir= and =gitdir= read-only.

A mount point cannot be renamed or removed (=EBUSY=).  The rule that makes
this hold: every directory from a protected path up to the root of the
writable share containing it must itself be a mount point.  That is why
=.git= is a share of its own.  See [[*Pitfalls]] for the tests behind it.

The main work tree of a linked worktree is automatically exposed read-only,
even outside =~/src=, subject to the usual denied-path rules.  Bare
repositories have no main work tree to expose.  Commits land in the shared
=.git= and show up on the host at once.
If =git worktree list= cannot identify the main work tree (for example with
=--separate-git-dir=), expose it explicitly in project configuration.

Because =config= is read-only, commands writing it fail: =git push -u= pushes
but warns =could not write config file=, and =git remote add= or
=git branch -u= fail outright.  Making =config= writable is not an option:
=core.fsmonitor=, =core.sshCommand=, filters and aliases there make host-side
git, such as shell prompts and editors, run commands.

The host's Git configuration stays outside, but for the identity in
=~/.gitconfig.local=, exposed read-only.  Its managed part,
=~/.config/git/config=, holds preferences (aliases, =core.fsmonitor=, whose
daemon socket lives in the shared =.git=, =status.aheadBehind = false=), and
applications write =~/.gitconfig=.  The container's =~/.gitconfig= is its own
instead, written at startup in the session's tmpfs home and dropped on exit:
it includes =~/.gitconfig.local= and sets =push.default=current= and the
Git LFS filter.  The agent may change it, and git reads =branch.*= and
=remote.*= from any scope, so it stands in for the repository's file for the
session:

| Instead of               | Run                                                                                          |
|--------------------------+----------------------------------------------------------------------------------------------|
| =git push -u origin B=   | =git push origin B=, then =git config --global branch.B.remote origin= and =branch.B.merge refs/heads/B= |
| =git remote add R URL=   | =git config --global remote.R.url URL= and =remote.R.fetch '+refs/heads/*:refs/remotes/R/*'=   |
| =git config KEY VALUE=   | =git config --global KEY VALUE=                                                              |

A =git-hooks= clause (see [[*Project configuration]]) sets =core.hooksPath=
in the same file, as hooks cannot be installed in the read-only =hooks/=.
uraj's host-side hook, which =scripts/coding_style/install-hooks= links
into the main work tree, is a deliberate exception to the read-only
=hooks/=: host-side commits run the work tree's check, which agents can
change.

With =push.default=current=, a bare =git push= pushes the current branch to
its namesake on =origin=, and =@{push}= resolves, without any upstream.

** direnv

=direnv= is among the container packages.  Its approvals live in the
tmpfs home, so they start empty; the launcher carries over a single one,
for the work tree's top-level =.envrc=, only when the host approved that
exact path.  Linked worktrees need an approval of their own path, which
they may inherit, see [[Inherited approvals]]; otherwise run =direnv allow=
in each worktree.

The approval is written as direnv records it, under
=~/.local/share/direnv/allow/=, and is dropped on exit; one the agent adds
stays inside the session.

The environment loads automatically:

- at startup, in the working directory, for the agent itself, so its own
  processes (MCP servers, Codex's app-server) and shell snapshots see it.
  A slow =.envrc= delays the agent's start; a blocked one only logs an
  error;
- again before each command, which may run in another directory or after
  =.envrc= changed.  Claude Code sources =$CLAUDE_ENV_FILE= after its shell
  snapshot, which would otherwise reset =PATH=; other agents' =bash -c= or
  =bash -lc= reads =BASH_ENV=, which steps aside when =CLAUDECODE= is set.
  Both run =direnv export bash= with status messages off; errors, such as
  a blocked =.envrc=, still show.  =sh= does not read =BASH_ENV=.

direnv 2.37 honours =DIRENV_LOG_FORMAT= only when it has a configuration
file, so the session gets an empty =~/.config/direnv/direnv.toml=.

* Agent specs

Specs are alists in =llm.scm= (Codex uses =codex-spec= in the launcher);
=~= stands for the home directory.

| Key        | Meaning                                                                                       |
|------------+-----------------------------------------------------------------------------------------------|
| =program=  | The real executable                                                                           |
| =arguments= | Arguments prepended to the caller's arguments                                                |
| =share=    | Paths shared read-write when they exist                                                       |
| =expose=   | Paths exposed read-only when they exist                                                       |
| =overlay=  | Directories writable for the session only, through a tmpfs overlay dropped on exit            |
| =persist=  | Paths within an =overlay= that do reach the host                                              |
| =seed=     | Files copied into the container's home, writable, dropped on exit                             |
| =preserve= | Regexps of environment variable names to keep                                                 |

Overlays are mounted inside the container by
=bwrap --dev-bind / / --overlay-src DIR --tmp-overlay DIR=, which needs no
privileges.  =persist= paths are first shared at
=/run/contained-agent/persist-N=, then bound back over the overlay by the
same =bwrap=.  =seed= files are exposed at =/run/contained-agent/seed-N= and
copied by the launcher script.

** OpenCode and Pi

Both are installed by the common Home services, including lappie's embedded
Home. =opencode= and =pi= run contained; the original commands remain in
=~/.guix-home/profile/bin/=. Pi is packaged from the official
=earendil-works/pi= release as =pi-coding-agent= (the executable is =pi=).

OpenCode reads =~/.config/opencode= through a temporary overlay. Its data
and state directories (=~/.local/share/opencode= and
=~/.local/state/opencode=) persist, including authentication and session
storage. Treat those writable directories as shared state across sessions.
Its cache is temporary.

Pi reads =~/.pi/agent= and =~/.agents/skills= through temporary overlays;
=~/.pi/agent/sessions/= and =~/.pi/agent/settings.json= persist. Model
choices and other settings therefore survive restarting the container.
Pi keeps its usual behavior: press =Ctrl+S= in =/model= to save the startup
default; an ordinary selection only affects the current session.
The launcher creates an empty settings file on first use without replacing
existing preferences. Log in with the original host command first: changes
to Pi credentials and extensions inside the container are discarded on exit.
The default agent directories are used; custom =PI_CODING_AGENT_DIR= and XDG directory overrides are not
forwarded. Both agents receive =OPENAI_.*=, =ANTHROPIC_.*=,
=GEMINI_API_KEY= and =OPENROUTER_API_KEY=. Other provider variables can be
added with a project's central =preserve= clause.

** Claude Code

Paseo's system tier currently uses this same policy; its host tier bypasses
contained-agent. Terminal =claude=/=codex= remain contained by default. See
[[file:paseo-daemon.org::*Configuration][Paseo provider and configuration management]].

- =~/.claude= is an overlay.  Settings (=settings.json= links to one of the
  =settings.json.*= profiles), plugins, skills and any new file such as
  =CLAUDE.md= are the session's own.
- Persisted: =projects/= (transcripts, memory), =sessions/=, =session-env/=,
  =file-history/=, =paste-cache/=, =todos/=, =plans/=, =tasks/=,
  =history.jsonl=.
- =~/.claude.json= (project trust, MCP servers) is seeded and dropped.
- Consequences: =/config=, =claude mcp add= and plugin installs work for the
  session only; change them on the host.  The command line may ask for
  project trust again; Paseo uses the SDK and does not.

** Codex

The launcher overlays =~/.codex= and =~/.agents/skills=.  Configuration,
trust decisions, rules, skills and plugins are writable inside a session and
discarded on exit.  A relative =config.toml -> config.toml.new-api= link works
because its target is in the same overlay.  Custom =CODEX_HOME= locations are
rejected.

Codex's runtime databases live in the persistent
=~/.codex/contained-sqlite/= directory, selected with the =sqlite_home=
command-line setting.  Keeping the directory as one mount places every
database beside its WAL, SHM and journal files, preserving SQLite locking
across concurrent sessions.  The top-level host databases are outside the
contained runtime.

The following state is shared with the host and other contained sessions:

- =contained-sqlite/= and =sqlite/=;
- =sessions/=, =archived_sessions/= and =thread-writer-locks/=;
- =log/= and =history.jsonl=;
- =auth.json= when it exists before launch.

A missing =history.jsonl= is created with mode =0600=.  When =auth.json= is
missing, login is valid for the current session only; log in on the host first
when credentials must persist.  Credential refreshes rewrite an existing
=auth.json= in place and pass through the bind mount.  =logout= removes the
file and must therefore run on the host after contained sessions exit.

=session_index.jsonl= remains in the overlay.  Codex replaces it atomically
when deleting a thread, which is incompatible with a single-file bind mount.
Thread-name index changes are consequently session-local; the rollout and
database state remain persistent.

On first startup, Codex indexes the shared active and archived rollouts into
the contained database before showing the trust screen.  Let this finish.  An
interrupted worker holds its backfill lease for 15 minutes, while a new process
waits only 30 seconds.  During that interval startup may report that the
database appears damaged.  After the worker has stopped and the lease expires,
start one instance and let it complete the import.  Do not delete the database
or mark an unfinished import complete.  The =~/.codex= path in the diagnostic
names the rollout source; the database remains in =contained-sqlite/=.

The integration test uses a temporary HOME, checks two consecutive overlays,
configuration symlinks, shared SQLite WAL state, credentials and sessions:

#+begin_src sh
CODEX_TEST_BINARY=/path/to/real/codex \
  python3 test/python/uraj/guix/contained-agent/contained-agent-codex.py
#+end_src

With =CODEX_TEST_BINARY= it exercises the real =config/batchWrite= trust
update and file login with a fake API key, imports active and archived rollout
fixtures, and resumes an expired backfill lease.  It checks that backfill is
complete before stopping the server.  Without it, the test checks the mount
behavior using local file operations.

* Project configuration

Clauses, in both places below:

- =(expose PATH ...)=, =(share PATH ...)=: extra mounts, skipped when
  the source is missing. Each entry can also be =(SOURCE TARGET)= to mount
  at a different container path. Both source and target expand =~/=;
  relative paths are relative to the current worktree root, even when
  launched from a subdirectory or inheriting the main work tree's policy.
  A plain =PATH= still uses the same source and target. Both ends of a
  mapping are subject to the denied-path checks.
- =(preserve REGEXP ...)=: host environment variables passed through when
  set.
- =(guix-daemon)=: opt into Guix nesting and daemon access, with an isolated
  project cache (details below).
- =(git-hooks DIR)=: =core.hooksPath= in the session's own =~/.gitconfig=,
  so git inside the container runs the hooks in =DIR=, relative to the work
  tree, instead of =.git/hooks=.  The read-only =.git/hooks= cannot take
  them, and host-side git keeps its own hooks.  uraj uses
  =(git-hooks "scripts/coding_style/hooks")=.

Central configuration only: =(podman-remote)=, =(ssh-agent ...)= and the
credential clauses =(github TIER)=, =(git-credential URL FILE)= and
=(env NAME ...)=, described below.

Central: =projects.scm=, keyed by the current work tree's canonical root.
A linked worktree without an entry inherits the entries of the checkout
Paseo created it from, if that checkout has any, and otherwise the main
work tree's.  The source comes from Paseo's registry
(=$PASEO_HOME/projects/{workspaces,projects}.json=, default =~/.paseo=),
which no container mounts; it counts only when it is a work tree of the
same repository.  A missing or unreadable registry falls back to the main
work tree.  An explicit worktree entry in any central source replaces that
fallback across all sources; even an empty =(project "PATH")= disables
inheritance.
It reaches the program through Home, so the
agent cannot change it, and changing it takes a reconfigure.

#+begin_src scheme
(project "~/src/uraj"
  (expose "/var/log" "/run/current-system" "/run/booted-system"
          "/var/guix/profiles" "~/.local/state/shepherd" "~/.guix-home"
          "~/.config/shepherd" "~/.config/guix"))
#+end_src

For example, share one ignored data directory across linked worktrees,
and expose reference data read-only at a worktree-relative location:

#+begin_src scheme
(project "~/src/uraj"
  (share ("~/src/uraj/instances" "instances"))
  (expose ("~/datasets/reference" "data/reference")))
#+end_src

These are container mounts; they do not create host-side symlinks. The
target need not exist, and a mount hides existing target contents for the
session. Worktrees with their own explicit project entry must include any
desired mappings themselves.

*** Fixed worktrees as permission presets

Create a branch and a sibling worktree with the common shell helper:

#+begin_src sh
fork-worktree ~/src/uraj maa
# Branch maa, directory ~/src/uraj-maa, starting at uraj's HEAD.
fork-worktree ~/src/uraj docs ~/workspaces/uraj-docs
# The optional third argument overrides the target directory.
git -C ~/src/uraj worktree list
#+end_src

After creating the worktree, the helper opens
=~/.config/contained-agent/projects.local.scm= with =$VISUAL=, then =$EDITOR=
as a fallback, or =vi= when neither is set.  Editor arguments are supported.
The file is created with private permissions if missing; existing content
is preserved.  A failed worktree creation does not open the editor.

Add an exact =(project "~/src/uraj-maa" ...)= entry on the host for its
required permissions instead of inheriting the main work tree's.  Subdirectory
launches use that worktree's root; symlink aliases resolve to the same root.
In Paseo, add this directory as a project and select =Local= to use it
directly.  =New worktree= in that project creates another path which
inherits this entry unless it has its own central entry.

Worktrees share Git objects and branches, but have separate working files
and indexes.  A branch normally cannot be checked out in two worktrees.
Remove a clean, unused worktree with =git -C ~/src/uraj worktree remove PATH=;
its branch remains.  Remove its host policy too when retiring the path.

Configure explicit entries for worktrees that need different permissions.
Run =contained-agent allow=
and =direnv allow= on the host in each worktree whose approvals it cannot
inherit (see [[Inherited approvals]]); approvals of unrelated checkouts are
not reused.  Restart sessions to apply the new policy.  Shared Git metadata
and the normal base sandbox remain; local approvals remain recorded per
worktree.

*** Additional central configuration

Host-private additions: =~/.config/contained-agent/projects.local.scm=.
Create this file on the host, preferably with mode =0600=.  It uses the same
=(project ROOT CLAUSES ...)= syntax as the managed central file.  Matching
entries from both files are appended; neither replaces the other's entry.
If absent, it is skipped.  Edits are read on the next launch, without Home
reconfigure or =contained-agent allow=.

A host can also keep such additions encrypted in the repository, as
=secrets/hosts/HOST/contained-agent.yaml=, which SOPS decrypts to
=/run/secrets/contained-agent/projects.scm= (see
[[file:../secrets/README.org][secrets/README.org]]).  It joins the other two
files with the same syntax and rules.  The launcher knows, from build time,
which hosts have one: there, it waits up to 10 seconds for the file, as an
agent may start at boot before SOPS is done, then fails rather than start
without it.

This is user-level central policy, *not* project-local configuration.  Keep
private paths, SSH identities and destinations here instead of in the public
repository.  The program reads it at runtime; Home does not import it into
the store.  Its parent directory is denied to container mount requests.
Only one =ssh-agent= clause per project is accepted across these files;
duplicates fail instead of silently overriding a policy.  Put that whole
clause in the private file when its contents are sensitive.

** Credentials

Central files alone may also hand credentials to a project.  Each names a
host file, read at every launch: one that appears later reaches the next
session without restarting anything.  A missing, unreadable or empty file is
skipped with a warning, and nothing of the host's stands in for it.  The
value never appears on a command line.  A project-local credential clause,
even approved, is a bad clause.

- =(github TIER)=: git over HTTPS and =gh= on github.com, with the token SOPS
  decrypts to =/run/secrets/github/TIER=.  Unlike other credential files,
  on Guix System, whose agent hosts all declare the tokens, a missing one
  is waited for, up to 10 seconds, and then fails the launch; on foreign
  distros, which have no SOPS service, the clause is skipped with a
  warning.  Tiers nest:

  | Tier       | Token                                    | Reaches                           |
  |------------+------------------------------------------+-----------------------------------|
  | =public=   | fine-grained, selected repositories      | your public repositories          |
  | =personal= | fine-grained, all repositories           | all your repositories             |
  | =world=    | classic, =repo= and =workflow= scopes    | every repository you can reach    |

  All may push (including workflow files) and open pull requests;
  only =world= may fork, or open pull requests on repositories of others.
- =(git-credential URL FILE)=: git over HTTPS below =URL=, which must start
  with =https://=.  git matches it as a prefix of whole path segments, so
  =https://github.com/OWNER= covers that owner's repositories, while
  =…/REPO.git= misses a remote spelled =…/REPO=.  These come before the tier:
  give an isolated project only this clause, or narrow one owner of a tier.
- =(env NAME (file FILE))=: the variable =NAME= set to =FILE='s contents.
  It overrides =preserve=, which passes the launcher's own environment: the
  host's value is dropped even when the file is missing.
- =(env NAME (value VALUE))=: the variable =NAME= set to =VALUE= as
  written.  Only in the private files, =projects.local.scm= and the
  SOPS-decrypted =projects.scm=; in the Home-managed =projects.scm=, which
  is in Git and the store, it fails the launch.  Like =(file FILE)=, it
  overrides =preserve= and never appears on a command line.

The token files of =github= and =git-credential= are each mounted alone,
read-only, at =/run/contained-agent/git-credential-N=.  The launcher
configures git through =GIT_CONFIG_COUNT=, read after =~/.gitconfig=: an
empty =credential.helper= drops the host's helpers (such as the one
=gh auth setup-git= installs), then each URL gets a helper that answers
=get= from its file and ignores =store= and =erase=.  The container's =gh=
is a wrapper that runs GitHub CLI with the token git gives for the current
repository's =origin=, or for github.com outside a repository.  An explicit
=GH_TOKEN= wins.  =gh -R OTHER/REPO= still uses the current repository's
token, which is the same one unless a =git-credential= clause applies.

Remotes must use HTTPS for these to apply; SSH remotes keep using the
=ssh-agent= clause, if any.  The tokens live inside a container with
network access: treat them as readable by anything the agent runs; their
scope is the protection.  [[file:../secrets/README.org][secrets/README.org]] covers requesting and rotating
them.  uraj uses =(github "personal")=.

Central configuration can select a manifest for this worktree:

#+begin_src scheme
(project "~/src/uraj-maa"
  (manifest ".guix/maa-manifest.scm"))
#+end_src

The =manifest= clause is accepted only in the managed or host-private
central project configuration.  Its path is relative to the worktree root,
not the launch directory.  Absolute paths, =.= or =..= components, symlinks,
missing files and multiple manifest clauses are errors, without fallback.
Both =contained-agent allow [DIRECTORY]= and session startup read the same
central selection.  Selecting a manifest does not approve its contents.

For a selection inside =.guix/=, approval still covers the whole =.guix/=
directory, including =contained-agent.scm= and sibling Scheme files, and
Guix uses the selected filename in the approved copy.  A selection elsewhere,
such as =(manifest "maa-manifest.scm")=, approves that file alone instead of
=.guix/=; it is copied to =manifest.scm= in the approval directory.  Any files
it loads are not covered by that approval.  Put related files under =.guix/=
when they need to be reviewed and copied together.

After editing the central selection, run =contained-agent allow= in that
worktree and restart the session.  Changed or unapproved contents are left
out with a warning; the launcher never falls back to the default manifest.

Without an explicit manifest selection, project-local files are
=.guix/contained-agent.scm= (same clauses at top level) and
=.guix/manifest.scm=, or a top-level =manifest.scm=.  The agent can write
them, and =guix shell= evaluates a manifest on the host, outside any
sandbox.  So they count only once approved:

1. =contained-agent allow= copies them to a staging directory, shows
   =git diff= against the last approved copy and asks on a terminal.
2. On =y= the copy is kept under its nar hash in
   =~/.local/state/contained-agent/approved/<encoded-worktree-path>/=.
3. A session hashes the current work tree's files and, on a match within
   that work tree's approval directory, loads the
   approved copy, never the work tree.  Otherwise it warns and starts
   without them.

The whole =.guix= directory is hashed, as a manifest may =load= its
siblings.  Links inside it are refused: they could reach unreviewed files.
A top-level =manifest.scm= is hashed alone, so anything it loads is not
covered.

<<Inherited approvals>>A new worktree takes over the approvals of a
checkout it inherits policy from: the one Paseo created it from, else the
main work tree, as for central entries.  Both registries are outside every
container.  It does so only when that checkout has approved, at its own
path, both the worktree's current project-local files (same nar hash) and
its current =.envrc= (as direnv names the approval), each where present.
Then the worktree's approval directory gets a link to the checkout's
approved copy, and the host's =~/.local/share/direnv/allow/= an approval of
the worktree's =.envrc=, so plain host shells load it too.  Nothing is taken
over otherwise, not even one of the two.

Sessions do this at startup; =contained-agent inherit [DIRECTORY]= does it
for host shells before any session, and reports what it found.

Requests never mount anything under these, nor any directory containing
one (such as =$HOME= or =/=): =~/.paseo=, =~/.paseo-password=, =~/.ssh=,
=~/.gnupg=, =~/.password-store=, =~/.config/contained-agent=,
=~/.local/state/contained-agent=, =~/.local/state/paseo-broker=,
=/var/guix/daemon-socket=, =/run/secrets=, =/run/user=.

* What agents cannot do

- Use SSH by default.  The optional central =ssh-agent= clause below grants
  access to a project's dedicated agent, not the host's normal agent or
  private key files.  GPG remains unavailable.
- Use =gh= or HTTPS git credentials by default, or ever with the host's
  login: =~/.config/gh= is not mounted and the host's credential helpers are
  dropped.  The optional central =github= clause above grants a tier.
- Reach the Guix daemon by default.  Projects opting into =(guix-daemon)=,
  including uraj, can build and use nested Guix environments.
- Control the user's Shepherd (=/run/user/UID=) or see host processes
  (separate PID namespace; mounting the host's =/proc= would expose other
  processes' environments).
- Read =/var/log/debug=, =secure= or =guix-daemon.log=: those are root-only
  even for the user; only =messages= is in =log-readers=.

* Local Podman runtime

The central =(podman-remote)= clause starts or reuses a project-owned rootless
Podman runtime next to the Guix agent container, reached through a filesystem
Unix socket.  It needs no SSH identity, extra account or ACLs, and is
independent of SSH clauses.

#+begin_src scheme
(project "~/Projects/20260929-traj-generation/traj-record"
  (podman-remote (tmpdir "~/.cache/harbor/tmp"))
  (share "~/.cache/harbor"))
#+end_src

The normal worktree/Git mounts, project share/expose clauses and explicit TMPDIR
are mounted at the same absolute paths in the runtime.  Nested Git protections
remain read-only mounts.  Agent state, credential mounts, SSH sockets and broad
common agent mounts are not implicitly passed to the runtime.  Missing paths
follow the ordinary project-clause rules; explicit TMPDIR is created before
launch.  Changes apply to new sessions: an existing runtime is never expanded
in place to pick up a different project's permissions.

The runtime receives the Podman API's full execution authority, but its outer
filesystem view limits available bind sources.  A request to bind / exposes
that runtime's root, not the host root.  Shared files use the host user's mapped
identity, so no ACLs or group permission changes are needed.  Paths
overlapping runtime infrastructure and host runtime state are rejected, and
agents can never mount runtime state or the host service's socket.
Mapped share/expose clauses bind their source at the mapped target, so the
runtime sees the paths the agent sees.  Both ends are checked; paths
containing =, colon, comma or newline are rejected instead of guessing how the
engine will parse them.

The agent manifest must supply podman and its chosen Compose provider.  The
launcher sets CONTAINER_HOST and DOCKER_HOST to
=unix:///run/contained-agent/podman/podman.sock= after direnv initialization,
installs a wrapper that selects remote mode, and mounts only the API socket
folder read-only into the agent.  There is no listening TCP port or SSH key.

** Host prerequisites and initialization

Home reconfiguration installs the Python supervisor and pins its Podman
executable through the Guix package closure.  The host needs the existing
=rootless-podman-service-type= setup: subordinate IDs, mapping helpers,
/dev/fuse, /dev/net/tun and permission to create a child of /sys/fs/cgroup with
cpu, memory and pids already enabled.  It does not request sudo or alter global
controller settings when those prerequisites are missing.

** Host Podman service

The outer engine of every runtime is one long-running rootless
=podman system service=, outside any agent session.  Sessions reach it through
its socket and never start Podman themselves.  This is required under the
Paseo broker: its supervisor runs the launcher in a user namespace mapping only
the user's own ID, where the subordinate-ID helpers cannot work, and its PID
namespace would kill a runtime started from a session when that session ends.

| Deployment                        | Started by                                                |
|-----------------------------------+-----------------------------------------------------------|
| Guix System with =paseo-service-type= | Root Shepherd service =contained-podman=, as the Paseo user, at boot |
| Home with Paseo autostart          | User Shepherd service =contained-podman=                   |
| Otherwise                          | =contained-agent podman-service= in a host terminal        |

The service has its own =containers.conf=, overlay storage and pause process
under =~/.local/share/contained-agent/podman/host/=, apart from the user's
ordinary Podman, so pruning or resetting that never reaches project runtimes.
Its socket is =RUNTIME_ROOT/host/podman.sock= and is never mounted into an
agent.  =RUNTIME_ROOT= is =/run/contained-podman/UID= when the system service
has created it at boot, before any login and unaffected by logout; otherwise
=$XDG_RUNTIME_DIR/contained-podman=.  A session fails with a hint when the
service is not running.  Stopping the service leaves running runtimes alone;
each is owned by its own conmon.

The same service stops idle runtimes.  Every minute it checks each runtime
without blocking: one is stopped, as by =podman-stop=, only when no startup
or session holds its locks, its last session left at least 30 minutes ago
(=--idle-minutes=), and its inner engine reports no running containers.
Detached tasks therefore keep a runtime alive; an unresponsive inner API does
not.  Images, volumes and storage are always retained.

Each runtime creates a dedicated host cgroup subtree.  The outer runtime is
rootless, uses a private cgroup namespace and a custom seccomp profile, and
does not use --privileged.  Its brief namespace-UID-0 bootstrap delegates only
the private cgroup management files to UID 1000, then drops UID/GID and clears
supplementary groups before starting the API.  Startup checks the service UID,
rootless status and active seccomp filter.  Service and task cgroups are separate.

The runtime image is pulled by the digest of quay.io/podman/stable:v5.8.7's
manifest list,
=sha256:2fb39ca923dd9e0ee33f9e319c3a107a2bfde022a6a31560cbd56a862821e7d3=, and
must match the verified image ID
=0e1abc5572ecd4dbc4574f60669bdbbafe804af7f6709b257cc93b8a797106ea= before it is
executed.  A tag would move: the host service's fresh store pulled a newer
:latest and failed this check.  A mismatch still fails closed; it does not
silently upgrade the runtime.
The underlying supervisor accepts explicit image/reference and expected-ID
arguments for a reviewed update.  The active API image is Podman 5.8.7; the
host client is the Guix Podman package.  This image pin is a compatibility pin,
not a signature/provenance verification system.

** Lifecycle and storage

The host supervisor connects the Guix agent to a persistent runtime, retaining
stdin, stdout, stderr and the agent exit status.  Sessions with the same project
and effective mount policy reuse one runtime and its writable image store.
The identity also includes the verified runtime image, host Podman executable,
user/subordinate IDs and mount source identities.  Different worktrees or
changed read/write permissions can therefore select different runtimes.  An
existing session's authorization is not revoked by changing new-session policy.

Sessions sharing a runtime share the full Podman API: container names, networks,
volumes and images are common, and one session can stop another's task.  Use
unique Compose project names for simultaneous Harbor runs.  This is one project
trust boundary, not isolation between agents authorized for that project.

Persistent state and logs live under
=~/.local/share/contained-agent/podman/<runtime-id>/=.  Socket and transient
engine state live under =RUNTIME_ROOT/<runtime-id>/= (see above).  Both
directories must be private to the user.  The outer container is named
=contained-agent-runtime-<runtime-id>= in the host service.
Startup prints the runtime ID and log location.  =contained-agent podman-list=
lists every runtime with its ID, whether its container is running, how many
sessions hold it, when it was last used, its project and writable mounts.  A startup lock serializes
creation/recovery; shared session locks prevent an ordinary stop while another
supervised agent session is attached.

Leaving a session does not stop the runtime; the host service stops it after
the idle period.  To stop it earlier, after all sessions exit:

#+begin_src sh
contained-agent podman-stop RUNTIME_ID
#+end_src

This stops its tasks and removes transient state and the private cgroup, while
retaining images, volumes and writable storage.  It refuses while a session
supervisor holds a lease.  Detached tasks do not hold session leases: stopping
an otherwise idle runtime also stops those tasks.  It waits up to 30 seconds
for conmon's cleanup to leave the private cgroup and otherwise reports the
remaining processes, never killing them; rerun it once they exit.  SIGKILL of a supervisor can
release its lease before a surviving agent exits; close such orphaned agents
before explicitly stopping the runtime.

After reboot, the next session recreates the service, socket and cgroup using
the persistent storage; cached images remain available.  It does not resume
old tasks automatically.  Old task metadata may remain and cause name conflicts.
An interrupted startup is retried on the next attachment when no session holds
a lease.  There is no automatic storage purge; unused policy versions retain
their own caches.  The host service and each inner engine use native rootless
overlay storage; the inner graphroot is a host bind mount, so no overlay is
stacked on another.  Startup fails unless the inner engine reports the
selected driver.  =--storage-driver=vfs= selects VFS for the inner engine; the
driver is part of the runtime identity, so switching selects separate storage.
All runtimes share the host service's copy of the pinned runtime image.  Inner
storage is shared only by clients of the same runtime, not by other runtimes
or the user's ordinary host Podman.  No shared read-only image library is
used.

Agents' Podman is a remote client, so the inner engine resolves image names.
Its only short-name search registry is docker.io, as with Docker: references
such as =alexgshaw/fix-git:20251031= in task definitions resolve without the
TTY that enforcing mode needs to choose among several registries.  The
image's short-name aliases still apply.  The client's and the host's
registries.conf have no effect here.  A running runtime picks this up when it
is next started.

** Self-check

#+begin_src sh
contained-agent podman-check RUNTIME_ID
#+end_src

This attaches to the runtime like a session, starting it if needed, so idle
collection cannot stop it meanwhile.  Through its inner API it then checks,
printing PASS or FAIL for each:

- that docker.io is the only short-name search registry;
- a build whose context the client uploads;
- a write through a same-path bind of the first writable directory mount,
  in a temporary =.contained-podman-check-*= directory removed afterwards;
- that every read-only mount refuses writes and a writable remount, in
  ordinary and privileged (read-only /sys) tasks.  Files are probed by opening
  them for append, so nothing changes even if the protection were missing;
- that binding / exposes the runtime's root, not the host's runtime state;
- service name resolution on a user network, which Compose relies on;
- memory, PID and CPU limits as the kernel reports them.

It pulls =docker.io/library/busybox:1.37= into the runtime's storage, and
removes its image tag, containers and network.  It exits non-zero when any
check fails; commands and output are in the runtime's =commands.log=.

** Harbor acceptance

The worktree already includes jobs/, instances/ and the apt-cacher files.
Sharing ~/.cache/harbor and its TMPDIR lets relative Compose binds resolve to
the same files from the agent and runtime.  No extra /jobs mount is needed.
Use project-local output paths and the configured TMPDIR for generated bind
sources; synthetic HOME and private /tmp files are not runtime bind sources.

A disposable host experiment (2026-10-25, lappie, overlay storage) passed the
same checks, plus Compose itself, before the host service replaced its local
outer engine; =podman-check= now covers them on the deployed path.  The
persistent runtime still needs concurrency/reboot smoke tests and a real
Harbor trial in traj-record.  Default privileged tasks are not promised: the
tested privileged variant explicitly binds /sys read-only.  A Guix-built
runtime image remains follow-up work.

* Optional Guix daemon access

The managed uraj entry includes =(guix-daemon)= so its sessions can run
=guix build=, =guix home/system build= and =guix time-machine=.  It may also
be added to host-private central configuration or an explicitly approved
project-local configuration:

#+begin_src scheme
(project "~/src/another-project"
  (guix-daemon))
#+end_src

This enables =guix shell --nesting=, which provides the running Guix and
daemon socket.  Ordinary requests to mount the daemon socket directly remain
denied.  The wrapper then applies these mappings *after* the project's other
mounts:

- A persistent per-project cache under
  =~/.cache/contained-agent/guix<canonical-project-path>/cache= replaces
  =~/.cache/guix=.  If the host uses =XDG_CACHE_HOME=, that nesting cache path
  is covered too.  The first launch seeds the cache from the host with
  =cp -a --reflink=auto=, guarded by a lock; later launches retain the project
  copy.  Changes never copy back.  Without reflinks the initial copy can
  consume substantial disk space.
- The user's =/var/guix/profiles/per-user/USER/profiles= and =inferiors=
  directories are writable for registering cached profile GC roots.  They
  deliberately override uraj's read-only =/var/guix/profiles= mapping.  These
  are shared host metadata, not project-private copies.

Daemon access is an explicit relaxation: it exposes the daemon protocol,
allows store operations and resource consumption, and lets fixed-output
builds use the daemon's network outside the session's network policy.  The
cache isolation avoids direct writes to host channel checkouts; it does not
turn daemon access into a restricted build API.

=python3 test/python/uraj/guix/contained-agent/contained-agent-guix.py= verifies opt-in, approved local
configuration, one-time independent cache seeding, XDG cache coverage and
mount ordering with real bind mounts.  It does not require a daemon.
After deploying, verify in a new uraj session with:

#+begin_src sh
guix build hello --dry-run
guix time-machine -C env/guix/channels-lock.scm -- describe
#+end_src

* Per-project SSH agents

Only the central =projects.scm= or host-private =projects.local.scm= may
declare =ssh-agent=.  Even an approved
=.guix/contained-agent.scm= cannot request it.  For example (replace these
example key paths with keys you provision on the host).  Put this in
=~/.config/contained-agent/projects.local.scm= to keep it out of Git and
the Guix store:

#+begin_src scheme
(project "~/src/uraj"
  (ssh-agent
    ;; Optional; defaults to ~/.ssh/known_hosts.
    (known-hosts "~/.ssh/known_hosts")
    (identity "~/.ssh/uraj-deploy"
      (destinations "git@github.com"))
    (identity "~/.ssh/dev-servers"
      (destinations "wenxin@a.xx.com" "wenxin@b.xx.com"))))
#+end_src

An optional =(client-config STRING)= holds literal SSH client configuration,
including multiline strings.  For example, inside the same =ssh-agent= clause:

#+begin_src scheme
(client-config "Host dev.example.com
    HostName 192.0.2.1
    User wenxin
    Port 23333
    HostKeyAlias [dev.example.com]:23333

Host github.com
    User git

Host *
    IdentitiesOnly no
    ForwardAgent no
    AddKeysToAgent no
    StrictHostKeyChecking yes
")
#+end_src

The corresponding identity still needs
=(destinations "[dev.example.com]:23333")=.  SSH client configuration does
not change how =ssh-add -h= looks up host keys.  =client-config= is text, not
a filename; quotes and backslashes use Scheme string escaping.  Only one
such clause is allowed.  Its contents are written to a mode-0600 file in the
project's private runtime directory and mounted read-only as =~/.ssh/config=.
The text is never shell-expanded or evaluated by SSH on the host.  It is
interpreted by SSH inside the container, including any commands it specifies.
If omitted, the generated config is empty.  Editing the string changes the
policy fingerprint and reloads the project agent on the next launch.  A live
agent keeps its socket and the config file is rewritten in place, so existing
containers also see the update.

Each =destinations= contains one or more alternatives.  Each becomes a
separate =ssh-add -h= argument for that identity.  No identity may omit its
destinations or supply an empty list.  Paths must be absolute or start with
=~/=.  Private keys remain on the host; the supplied client config, public
host-key data and selected agent socket enter the container.

After Home reconfigure, normal agent startup automatically starts the
project's SSH agent and loads its configured keys on the host, before entering
the container.  Later sessions reuse it while the configuration is unchanged.
The following host commands are optional management tools:

#+begin_src sh
contained-agent ssh-start ~/src/uraj   # explicitly reload keys, or unlock in advance
contained-agent ssh-socket ~/src/uraj   # prints the host socket path
# Stop it; a later session with ssh-agent configured will start it again:
contained-agent ssh-stop ~/src/uraj
#+end_src

=ssh-start= starts a dedicated background OpenSSH agent and loads the keys;
encrypted keys use ssh-add's terminal/askpass prompt.  It prints the socket
path, never shell code to evaluate.  A failed key load stops the new agent.
Starting it again reuses the live process/socket, runs =ssh-add -D= to clear
all identities (including manually added ones), then loads the current policy.
The config and known_hosts files are also updated in place to preserve existing
bind mounts.  A successful reload needs no container restart.  Reload is not
atomic: new authentication may briefly fail while keys are absent or loading;
existing SSH connections remain established.  If clearing or loading fails,
the agent is stopped so no partial set of keys remains.  Reopen containers
after a stopped/dead agent is recreated, since that produces a new socket inode.
Agents otherwise persist between sessions until
stopped or the host shuts down; this is not a Shepherd autostart service.

The host socket is
=$XDG_RUNTIME_DIR/contained-agent/<32-hex-path-hash>/ssh.sock=.  If
=XDG_RUNTIME_DIR= is unset, =/run/user/UID= is used; the runtime directory
must already exist, belong to the user, and be private.  The hash uses the
canonical current work tree path, so linked worktrees get separate agents
and sockets, even when they share a Git repository.  No extra project
name is needed.  A host-side lock serializes lifecycle operations.

Session startup checks, under the project lock, for an agent with a matching
policy and known_hosts snapshot.  A missing agent is started; a changed policy
or known_hosts file clears and reloads its keys automatically.  Concurrent
launches reuse the same process; the project lock serializes reloads.
Replacing key material at the same filename also requires =ssh-start=.
=--version= and =auth status= probes skip SSH provisioning.  Encrypted keys still require
ssh-add's terminal or host askpass prompt.  Automatic loading has stdin set
to =/dev/null= and stdout redirected to stderr so it cannot consume or corrupt
Paseo's protocol stream.  Without an available unlock mechanism it fails and
suggests =ssh-start= on the host; no partial agent is kept.  To permanently
disable automatic SSH access, remove the central clause and stop the agent.

The above host lifecycle applies to direct terminal use.  The
[[file:paseo-broker.org][Paseo broker]] instead keeps a separate shared SSH service outside session
namespaces.  It unlocks once per project and unchanged policy during a broker
lifetime; closing a session does not remove those keys.  Broker shutdown clears
that service.  Its PID records are isolated from direct host =ssh-start= and
=ssh-stop=, so those commands do not manage the broker's SSH cache.

In the container:
- =SSH_AUTH_SOCK=/run/contained-agent/ssh.sock= selects only this project.
- The socket is an individual read-only bind mount (read-only does not
  prevent socket connections).  No parent runtime directory is exposed.
- A read-only snapshot is mounted as =~/.ssh/known_hosts=; it reveals the
  entries in the selected known_hosts file.  Use a dedicated file to limit
  that list.  Private keys and the host's original SSH config remain absent.
- The optional =client-config= string supplies the container's =~/.ssh/config=.
  Put connection settings here rather than inheriting the host's IdentityFile
  or forwarding configuration.
- =openssh= joins the container packages.  Normal =ssh= and Git SSH remotes
  use the socket and known_hosts without additional flags.

An empty =(ssh-agent)= clause creates an empty agent for manual host-side
loading.  Use =SSH_AUTH_SOCK="$(contained-agent ssh-socket DIR)" ssh-add ...=.
In this mode it is your responsibility to pass =-h= constraints when loading
keys.  The container can use the socket's management operations too (for
example, deleting loaded keys); this is not a signing-only proxy.

** Destination patterns

Constraints use the native [[https://man.openbsd.org/ssh-add.1][ssh-add(1)]] syntax, including =user@host= and
=source>user@destination= forwarding hops.  Strings are passed as arguments,
never expanded by a shell.

For a non-default port, match the known_hosts spelling, for example
=(destinations "[hypie.example.com]:23333")=.  This selects the host-key
record; the SSH connection still needs =-p 23333=.  Loading errors preserve
ssh-add's original stderr and include the identity path, destination list,
and source known_hosts path.  They are not assumed to be password errors.

Wildcards such as =*.xx.com= need compatible known_hosts records; ssh-add
does not enumerate ordinary =a.xx.com= and =b.xx.com= records to expand the
pattern.  A usual wildcard setup uses a trusted host-certificate CA entry
such as =@cert-authority *.xx.com KEY=.  Without that setup, list individual
hosts.  Missing host keys fail loading; the wrapper never fetches or trusts
host keys automatically.  Hosts are authenticated by keys/certificates,
not merely by a DNS suffix.  A constraint to =git@github.com= does not limit
repositories: use a repository-scoped deploy key for that.

** Verification

=python3 test/python/uraj/guix/contained-agent/contained-agent-ssh.py= uses disposable keys, fake HOME,
temporary repositories and real OpenSSH processes.  It needs Guile 3,
OpenSSH 8.9+, Git, Bash, bubblewrap and sha256sum on PATH.  It exercises per-project
isolation, multiple identities/destinations, wildcard CA records, linked
worktrees, additive public/private configuration, automatic startup/reuse,
concurrent launches, policy reload,
encrypted-key failure cleanup, launch arguments, and
the SSH protocol through a read-only socket bind in a mount namespace.
Guix argv is captured rather than building a profile; no daemon, external
network, or real user keys are used.

* Pitfalls

Each of these was hit or tested while building this.

** Paseo
- Codex is launched without a working directory; the session directory comes
  over JSON-RPC and in =PASEO_AGENT_CWD=, which children inherit.  An early
  test run from inside a Paseo session therefore ran in the wrong
  repository and committed there.
- The version probe runs =COMMAND[0] --version= and drops the other
  elements of a command override.  With =["contained-agent", "codex"]= the
  probe failed, Paseo concluded Codex was too old and rejected its default
  =auto-review= mode.  Hence one executable per agent, named after it.
- Paseo 0.10.3 gives this probe only five seconds.  The launcher handles
  exactly =--version= by executing the configured agent binary directly,
  without project policy, credentials or a Guix container/profile build.
  A cold profile must not make a recent Codex look too old for =auto-review=.
  All other invocations still use the container, including =auth status=.
  Restart the daemon after deploying this fix to clear a cached failed probe.
- Paseo kills agents with =tree-kill=, which reaches processes inside the
  container; =SIGTERM= to the =guix= process alone does nothing.

** Guix
- =home-dotfiles-service-type= imports files with =local-file=, which
  follows links: a link in the dotfiles tree becomes a copy.  Use a
  =computed-file= that is itself a link.
- Invoked through a store path the program name is =HASH-codex=; the hash
  is stripped before dispatching.
- =guix shell -C= mounts options in command-line order; a later mount covers
  an earlier one.  User mappings come after =--nesting='s.
- Inside the container =HOME= comes from =passwd=, not the caller's
  environment: tests with a fake =HOME= must use absolute paths.
- =execlp= replaces the process before Guile flushes the error port:
  warnings need =force-output=.
- =--nesting= shares the host's =~/.cache/guix= read-write: the channel
  checkouts that host-side =guix pull= and =time-machine= evaluate.  The
  optional =guix-daemon= clause covers this with a project-specific cache,
  mounted after nesting's mappings.  See [[*Optional Guix daemon access]] for
  the remaining tradeoffs.

** Mounts
- Guix's synthetic home tmpfs can start with mode =1777=.  OpenSSH rejects
  this when discovering =~/.ssh/config= by default.  The container bootstrap
  changes only that synthetic home directory to =0700= before starting the
  agent; it does not recursively chmod mounted host data.  An explicit
  =ssh -F FILE= test does not cover this permission check, so the regression
  test also exercises default config discovery.
- A read-only mount point inside a writable share can be escaped by
  renaming its parent: =mv .git .git.x= and recreate =.git= with a
  malicious =config= or hook.  Directories created by Guix for mount points
  live in the container's tmpfs and are harmless.
- Mounts follow links, so a link cannot be pinned read-only.
  =~/.claude/settings.json= is a link: the link itself could be replaced
  even though its target was read-only.  Hence the overlay for =~/.claude=.
- An overlay's lower directory must hold no mount points, or the mount fails
  with =EINVAL= (tmpfs and btrfs alike).  Hence =persist= paths mounted
  aside and bound back.
- A single-file mount cannot be renamed over.  Claude's atomic writes fall
  back to writing in place; tools without such a fallback fail.
- SQLite creates and deletes =-wal=, =-shm= or =-journal= files next to the
  database.  Persisting the database file alone leaves those in the
  overlay: committed data is lost, and concurrent sessions each get their
  own =-shm=, which breaks locking and can corrupt the database.  A database
  must persist with its whole directory.

** Agents
- Codex's own =workspace-write= sandbox (Paseo's =auto= mode) makes =.git=
  entirely read-only.  Failures there do not say whether our layer would
  have stopped them; test with =full-access= to see our layer alone.
- =node_repl= processes from the =codex-desktop= store item are MCP servers
  that =config.toml= points at, started by contained Codex sessions; they
  do not mean the desktop app is running.
- Plugin caches in an overlay: a marketplace update is downloaded again by
  every session until a host-side Codex syncs it.
